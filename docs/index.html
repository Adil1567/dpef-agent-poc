Part 1

What is OpenSpec?

AI coding assistants are powerful but unpredictable when requirements live only in chat. OpenSpec adds a lightweight planning layer so you and your AI agree on what to build before any code is written — and that agreement is a set of files checked into git, not a conversation that evaporates.

The core idea

Every change to a codebase starts as a small set of markdown files:

FileAnswers
proposal.mdWhy are we doing this? What's changing?
specs/What should the system do? — requirements & testable scenarios
design.mdHow will we build it? — architecture, trade-offs
tasks.mdWhat's left to do? — a checklist

The AI reads and writes these files as it works. Because they're just markdown in your repo, they're reviewable in a pull request like any other change — no special tool required to read them.

The two directories

openspec/ ├── specs/ # source of truth: how your system currently behaves │ └── auth/ │ └── spec.md └── changes/ # work in progress: one folder per change └── add-dark-mode/ ├── proposal.md ├── specs/ # "delta" specs — only what's changing ├── design.md └── tasks.md

specs/ never gets touched directly while a change is in progress. Each change proposes a delta — new requirements, modified requirements, removed requirements. When the change is finished and archived, the delta merges into the real specs/, and the folder moves to changes/archive/ for history.

The everyday loop

AI ASSISTANT CHAT
You: /opsx:propose "add dark mode"
AI:  Created openspec/changes/add-dark-mode/
     ✓ proposal.md — why we're doing this, what's changing
     ✓ specs/       — requirements and scenarios
     ✓ design.md    — technical approach
     ✓ tasks.md     — implementation checklist
     Ready for implementation!

You: /opsx:apply
AI:  Implementing tasks...
     ✓ 1.1 Add theme context provider
     ✓ 1.2 Create toggle component
     All tasks complete!

You: /opsx:archive
AI:  Archived to openspec/changes/archive/2026-09-03-add-dark-mode/
     Specs updated. Ready for the next feature.

Three commands, typed in your AI assistant's chat — not the terminal: /opsx:propose, /opsx:apply, /opsx:archive. That's the whole loop for a huge fraction of real work.

Why not just use "planning mode"? Planning mode in a chat is great for thinking through an approach — but the moment the conversation ends, so does the plan, unless something writes it down. OpenSpec is the thing that writes it down, in a form any future session, developer, or tool can read back without the original conversation.

Part 2

The gap after code ships

OpenSpec gets you from an idea to implemented, checked-off tasks. What it has no native answer for is everything that happens after.

  • Opening the pull request
  • Handling review comments
  • Deciding whether a comment means "the code has a bug" or "the spec itself was incomplete"
  • Making sure a change never gets archived while its PR is still sitting there, unreviewed

Here's what that gap looks like without any special handling:

Team writes a proposal, specs get approved, tasks get implemented. PR opens. Reviewer leaves a comment two weeks later: "Also track login attempts?" Nobody's watching the PR. A month later someone archives the change anyway.

Now the spec doesn't mention login attempts, the code doesn't either, and nobody remembers this was ever raised. Specs and code have drifted apart.

Nothing about openspec status even knows a PR exists. That's the gap this extension closes.

Part 3

The PR lifecycle extension

We added one new artifact — pr — to the same planning graph as proposal, specs, design, and tasks, and one new skill that owns its entire lifecycle: opening it, polling it, triaging every comment, and reconciling its real GitHub status before archive is ever allowed to proceed.

Before vs. after

BEFORE Proposal ──► Specs ──► Design ──► Tasks ──► [implement] ──► ??? (invisible to OpenSpec) AFTER Proposal ──► Specs ──► Design ──► Tasks ──► Verify ──► PR (first-class artifact) │ ┌───────────────┴──────────────┐ ▼ ▼ Comment = Bug Comment = Spec Gap → fix code, push → update spec first, then re-implement │ │ └───────────────┬───────────────┘ ▼ Merged on GitHub ▼ Archive — blocked until merged (hard guardrail)

openspec status now sees the PR. Archive refuses to run if it's still open. All of this comes from one schema file — nothing is hardcoded to this specific repo, which means it's copy-paste portable to any team using OpenSpec.

The new artifact

Same mental model as every other OpenSpec artifact: it has a template, an instruction, and dependencies.

ArtifactPurposeRequires
proposal.mdWhy + what's changing—
specs/Delta specs, what the system doesproposal
design.mdHow to build itproposal
tasks.mdImplementation checklistspecs, design
verify.mdTest results (pass/fail)tasks
pr.mdPR URL, status, CI, review logtasks, verify

This lives in openspec/schemas/spec-driven-pr/schema.yaml:

- id: pr generates: pr.md description: Pull request tracking (PR URL, status, review outcome) for this change instruction: | Invoke the openspec-pr-lifecycle skill to open a pull request for this change's implemented branch. Record the PR number and URL returned by the skill into pr.md using the template. Do not open the PR yourself or call GitHub APIs directly from this instruction - delegate to the skill. requires: - tasks - verify

Because pr requires verify, you can never accidentally open a PR for code that hasn't been tested — the artifact stays blocked until verify passes.

Full demo walkthrough

Step 1

Create a change with the PR schema

TERMINAL
$ openspec new change "add-dark-mode" --schema spec-driven-pr
✓ Created openspec/changes/add-dark-mode/
TERMINAL
$ openspec status --change add-dark-mode --json
{
  "artifacts": [
    { "id": "proposal", "status": "blocked", "requires": [] },
    { "id": "specs",    "status": "blocked", "requires": ["proposal"] },
    { "id": "design",   "status": "blocked", "requires": ["proposal"] },
    { "id": "tasks",    "status": "blocked", "requires": ["specs", "design"] },
    { "id": "verify",   "status": "blocked", "requires": ["tasks"] },
    { "id": "pr",       "status": "blocked", "requires": ["tasks", "verify"] }
  ]
}

Everything blocked, dependency chain visible directly in the JSON — this is the schema, not something hand-written for this change.

Part 5

Why not a standalone skill?

We already have a standalone example in this same repo — dpef-init / dpef-build-feature. That pair works, and it's a legitimate pattern. But it hand-rolls its own state machine, its own YAML file per feature, its own script to enforce valid transitions — and none of it is visible to openspec status. A separate system living alongside OpenSpec, not integrated with it.

What we built instead treats the PR as just one more node in the same planning graph as the proposal, the specs, the design, and the tasks. That means we get everything OpenSpec already does — dependency tracking, a generic status/instructions API, the archive-and-sync workflow, git-reviewable history — for free, instead of reimplementing it. A team that already uses OpenSpec for planning doesn't need to learn a second system; the PR step just shows up as the natural next step after tasks, using the exact same commands they already know.

Standalone skill

Own state machine, own file format, own transition script. Invisible to openspec status. A second system to learn and maintain.

Built into OpenSpec

PR is a node in the same graph. Dependency tracking, status, and archive workflow all come for free. No new mental model.

The trade-off worth being honest about: this only pays off if you're already using OpenSpec for planning. If a team's whole workflow is one narrow, repeatable task, a hand-rolled skill is genuinely simpler and has less surface area to break. But for general software development — where proposals, specs, and tasks already need to live somewhere reviewable — building PR lifecycle in as a native part of that same system is what actually simplifies day-to-day work: one workflow, one set of commands, one place to look for the state of any change, from idea to merged PR.

Part 6

Extending to other domains

The schema only defines shape — artifacts and dependencies — not implementation. That's what makes it extend cleanly to situations far beyond a single web app team.

Different data products, different rules

Create another schema, e.g. spec-driven-data-product, with its own artifacts (data-specs, dbt-implementation, data-validation) and its own skills. It lives in the same repo, shows up in the same openspec status, but follows completely different domain rules internally. A repo can hold as many schemas as it has kinds of work — a traditional service and a data pipeline can sit side by side, each tracked the same way at the top level.

External agents — e.g. a Databricks job monitor

Integrate through a skill, not by changing OpenSpec itself. A skill like openspec-databricks-monitor would read pr.md to find the relevant job, poll the Databricks API for its status, and write results back into the same Review Log the comment-triage step already updates. OpenSpec never needs to know Databricks exists — the skill is the translation layer between the external system and the shared file format.

Keeping documentation from going stale as the repo grows

Treat docs like code:

  • Auto-generate reference material (a list of schemas, a list of skills) from the actual files in CI, so it can't silently drift from what's real.
  • Give each schema a version and a changelog, so upgrades are explicit and migrations can be scripted rather than guessed at.
  • Run a CI check for stale markers (TODO, FIXME) and broken cross-references in docs the same way you'd lint code.

The common thread across all three: OpenSpec's job is to track dependencies and status generically. Anything domain-specific — data pipelines, external monitoring, custom validation rules — gets pushed into a schema or a skill, never into OpenSpec's core. That's what keeps the core simple even as the number of teams and domains using it grows.
